# FurnitureEPR

سامانه مدیریت سفارش و گردش تولید کارگاه مبلمان و محصولات خواب؛ با تمرکز بر ثبت سفارش، پیگیری مراحل تولید، کنترل کیفیت و تحویل به مشتری.

## وضعیت فعلی

- بک‌اند ASP.NET Core / .NET 10 با معماری لایه‌ای و CQRS.
- فرانت‌اند Angular 20 و Angular Material، فارسی و RTL.
- بررسی خودکار ساخت بک‌اند و فرانت‌اند در GitHub Actions فعال است.
- پس از تغییرات امنیتی و ارتقای وابستگی‌ها، ساخت بک‌اند و فرانت‌اند در GitHub Actions موفق شده‌اند. این نتیجه به‌تنهایی جایگزین آزمون انتهابه‌انتها روی محیط عملیاتی نیست.

## محدوده سامانه

### داخل محدوده
- تعریف مشتری، دسته‌بندی محصول، محصول و اجزای تشکیل‌دهنده محصول.
- تعیین تعداد پیش‌فرض اجزای محصول و امکان تغییر تعداد در سفارش.
- ثبت سفارش، مبلغ کل، تخفیف و مبلغ نهایی به ریال.
- تعریف گردش‌کار و نسخه‌بندی مراحل و مسیرهای مجاز.
- اجرای گردش‌کار سفارش، مشاهده تاریخچه، کنترل کیفیت و صف کارهای تولید.
- تعریف چند انبار، تخصیص تعداد هر قلم سفارش به یک یا چند انبار و مشاهده محل نگهداری محصول؛ این قابلیت فقط ردیابی محل است و شامل موجودی‌گردانی، ورود/خروج کالا یا حسابداری انبار نیست.
- تعریف کاربران، نقش‌ها و دسترسی‌ها.

### خارج از محدوده فعلی
- حسابداری و امور مالی، کنترل موجودی و عملیات کامل انبارداری، حقوق و دستمزد و درگاه پرداخت. ثبت محل نگهداری محصول در انبارهای تعریف‌شده، به‌عنوان بخشی از گردش سفارش، در محدوده قرار دارد.
- اجرای واقعی مراحل موازی تولید؛ مدل فعلی اجرای ترتیبی دارد و برای موازی‌سازی به مدل Branch/WorkItem نیاز است.

## اجزای مخزن

- `src/`: پروژه‌های بک‌اند .NET.
- `tests/`: تست‌های بک‌اند.
- `frontend/FurnitureEPR.Angular/`: پنل وب Angular.
- `docs/architecture/workflow-runtime.md`: شرح معماری و محدودیت‌های اجرای گردش‌کار.
- `.github/workflows/`: بررسی خودکار ساخت و تست.

## اجرای بک‌اند

پیش‌نیاز: .NET SDK 10.0.402 یا جدیدتر از شاخهٔ 10، SQL Server و پیکربندی امن محیط اجرا. **پروژه هنوز migration اولیهٔ EF Core ندارد**؛ ایجاد/به‌روزرسانی schema پایگاه داده باید قبل از اجرای کامل سامانه آماده شود.

```bash
dotnet restore src/FurnitureEPR.Presentation/FurnitureEPR.Presentation.csproj
dotnet restore tests/FurnitureEPR.Model.Tests/FurnitureEPR.Model.Tests.csproj
dotnet build src/FurnitureEPR.Presentation/FurnitureEPR.Presentation.csproj --configuration Release --no-restore
dotnet test tests/FurnitureEPR.Model.Tests/FurnitureEPR.Model.Tests.csproj --configuration Release --no-restore
```

در حال حاضر فایل Solution یک ورودی قدیمی از نوع ASP.NET Website برای پوشه Angular دارد؛ به همین دلیل در CI لینوکس، Restore کل Solution انجام نمی‌شود و پروژه‌های واقعی بک‌اند و تست جداگانه Restore می‌شوند.

### تنظیمات امن بک‌اند

پیش از اجرا، کلید JWT واقعی و تصادفی با حداقل 32 کاراکتر را از User Secrets یا متغیر محیطی `Jwt__Key` تنظیم کنید. مقدار placeholder موجود در `appsettings.json` عمداً توسط برنامه رد می‌شود. برای ساخت اولین مدیر، `IdentitySeed__Enabled=true` و مقادیر امن `IdentitySeed__AdminUserName`، `IdentitySeed__AdminEmail` و `IdentitySeed__AdminPassword` را فقط از متغیرهای محیطی یا Secret Store فراهم کنید؛ رمز مدیر را در مخزن ثبت نکنید. در محیط غیرتوسعه، مبدأهای مجاز فرانت‌اند را با `Cors__AllowedOrigins__0` (و در صورت نیاز اندیس‌های بعدی) تنظیم کنید؛ برنامه در صورت نبودن این تنظیمات در محیط غیرتوسعه اجرا نمی‌شود. همهٔ endpointها به‌صورت پیش‌فرض نیازمند احراز هویت هستند؛ `/api/auth/login` و `/api/health` عمومی‌اند. تعریف گردش‌کار و اتصال آن به دسته‌بندی به مجوز `workflow.manage` نیاز دارد. کنترل دسترسی صفحه‌های تعاریف محصول و دسته‌بندی در حال حاضر در Angular انجام می‌شود؛ برای امنیت کامل باید مجوز اختصاصی این عملیات در خود API نیز اعمال شود.

## اجرای فرانت‌اند

پیش‌نیاز: Node.js 22.

```bash
cd frontend/FurnitureEPR.Angular
npm install
npm start
```

آدرس API در تنظیمات محیطی فرانت‌اند تعیین می‌شود. برای اجرای کامل، بک‌اند و پایگاه داده نیز باید در دسترس باشند.

## مسیرهای اصلی API

پیشوند معمول endpointها `/api` است.

| قابلیت | مسیرهای نمونه |
|---|---|
| مشتریان | `GET/POST /api/customers` |
| دسته‌بندی‌ها | `GET/POST /api/categories` |
| محصولات | `GET/POST /api/products` |
| اجزا | `GET/POST /api/components` |
| اجزای محصول | `POST /api/products/{productId}/components` |
| سفارش‌ها | `GET/POST /api/orders` |
| نهایی‌کردن سفارش | `POST /api/orders/{id}/finalize` |
| مدیریت گردش‌کار | `GET /api/workflows`, `GET /api/workflows/{workflowId}` و زیرمسیرهای POST نسخه، مرحله، انتقال و انتشار |
| کارهای تولید | `GET /api/orders/production/tasks` |
| انبارها | `GET/POST /api/warehouses`, `PUT /api/warehouses/{id}`, `PATCH /api/warehouses/{id}/active` |
| تخصیص محل نگهداری | `PUT /api/orders/items/{orderItemId}/warehouse-allocations` |
| کنترل کیفیت | `POST /api/orders/{orderId}/workflow/{categoryId}/quality-control` |

فهرست گردش‌کارها با صفحه‌بندی و جست‌وجوی نام/کد ارائه می‌شود؛ جزئیات هر گردش‌کار شامل نسخه‌ها، مراحل، مسیرها و شناسه دسته‌بندی‌های متصل است. همه endpointهای گردش‌کار تحت مجوز `workflow.manage` قرار دارند. مدیریت تعریف انبارها نیز با همین مجوز انجام می‌شود؛ تخصیص محصول به انبار به مجوز `workflow.move` نیاز دارد و فقط وقتی مجاز است که گردش‌کار دسته‌بندی در مرحله‌ای با کد `WAREHOUSE` باشد. هر قلم سفارش می‌تواند بین چند انبار تقسیم شود، به شرط آنکه مجموع تعداد تخصیص‌یافته از تعداد سفارش بیشتر نباشد. برای جزئیات دقیق قراردادهای درخواست و پاسخ، به Controllerها و DTOهای متناظر در بک‌اند مراجعه کنید.

## وضعیت و کارهای باقی‌مانده

موفقیت CI یعنی کد در محیط GitHub Actions نصب/ساخت شده و تست‌های تعریف‌شده در workflow بک‌اند موفق بوده‌اند. این وضعیت به معنی تأیید کامل تجربه کاربری یا تست یکپارچه همه سناریوهای کسب‌وکار نیست.

پیش از بهره‌برداری باید دست‌کم موارد زیر تکمیل و تأیید شوند:
1. اجرای end-to-end ثبت سفارش از ابتدا تا انتهای تولید و تحویل با پایگاه داده واقعی.
2. تست یکپارچهٔ سیاست احراز هویت پیش‌فرض، مجوز مدیریت گردش‌کار و مجوزهای QC/انتقال/تکمیل.
3. ایجاد و بازبینی migration اولیه، سپس اجرای آن و آزمون روی SQL Server محیط مقصد.
4. بررسی رابط کاربری روی موبایل با نقش‌های واقعی کاربران کارگاه.
5. افزودن تست‌های یکپارچه برای سفارش، انتقال مراحل، QC و تکمیل گردش‌کار.
6. مشخص‌کردن فرآیند واقعی کارگاه؛ اجرای موازی هنوز پشتیبانی نمی‌شود و نباید پیش از مدل‌سازی دقیق وعده داده شود.
7. پیکربندی CORS originهای محیط استقرار و اجرای آزمون نهایی روی دستگاه موبایل.
8. افزودن تست‌های یکپارچه برای endpointهای فهرست و جزئیات گردش‌کار و سناریوهای نسخه‌بندی/اتصال دسته‌بندی.
9. تولید و اجرای migration مربوط به جداول انبار و تخصیص انبار روی SQL Server؛ migration باید پیش از اجرای قابلیت انبار اعمال شود.

## CI

- Frontend CI: نصب وابستگی‌ها و اجرای `npm run build`.
- Backend CI: Restore مستقل پروژه‌های بک‌اند و تست، Build بک‌اند و اجرای پروژه تست `FurnitureEPR.Model.Tests`.
- اجرای CI روی آخرین تغییرات باید از وضعیت شاخه `feature/project-initialization` بررسی شود؛ وضعیت موفق یک Commit قدیمی، جایگزین نتیجه Commit جدید نیست.
- وابستگی‌های ASP.NET Core و EF Core به نسخهٔ سرویس‌دهی `10.0.13` ارتقا یافته‌اند.
